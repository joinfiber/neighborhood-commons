An open layer for everything that happens in a neighborhood.

Six typed atoms — events, organizations, places, persons, broadcasts, curated lists — that any app can read, mix, and remix. Schema.org-aligned. Verified contributors. Public reputation graph. Read free, no key required.

Read free.

Every endpoint is open. No API key required for reads. The 1.0 spec is committed to additive-only stability — what works today works in 18 months.

02 — Composable

Apps as surfaces.

The Commons isn't a destination. Each app composes its own slice through opt-in filters: by verifier, by contributor, by proximity, by type. Same data, different editorial.

When a business gets verified through one app, every other app can honor that verification — or filter it out. The reputation graph is public; verifiers earn or lose trust on the quality of their approvals.

1Quick Start

You can read every endpoint without authentication. Start here.

Read events near a point

$ curl "{{baseUrl}}/api/v1/events?near=39.97,-75.14&radius_km=2&limit=5"

Returns up to five published events within 2 km of the supplied coordinates. Response shape: { meta, events }. Every event is self-contained — no further joins required to render it.

Filter by type and verification

$ curl "{{baseUrl}}/api/v1/organizations?kind=local_business&verified=true"

Returns organizations whose kind is local_business and which have at least one active verified identifier. Add verified_by=Holler,Merrie to restrict to verifications issued by specific apps.

Read what's broadcasting right now

$ curl "{{baseUrl}}/api/v1/broadcasts?near=39.97,-75.14&radius_km=1"

Active broadcasts only — expired and retracted broadcasts are filtered server-side. Response includes the embedded organization and location for each broadcast.

Inspect the reputation graph

$ curl "{{baseUrl}}/api/v1/verifiers"

Returns one entry per app that has ever issued a verification: approval count, active count, revoked count, methods used. Use this output to compose your own verified_by trust policy.

Calendar feed

{{baseUrl}}/api/v1/events.ics

Standards-compliant iCalendar feed. Drop the URL into Google Calendar / Apple Calendar / any RFC 5545 reader. RSS available at /api/v1/events.rss.

Writing data? Skip to Writing data for the service-tier flow. There is no self-service write path; service keys are operator-issued.

2Types

The 1.0 substrate is six typed atoms. Each maps to a Schema.org concept. Every response shape is self-contained — no implicit knowledge, no extra joins required to interpret a record. Field names follow Schema.org canonical (camelCase) on output; database columns underlying them are snake_case.

TypeSchema.orgWhat it represents
PlacePlacePhysical location — venue, park, address.
OrganizationOrganization · LocalBusinessCollective entity — business, community group, nonprofit, curator.
PersonPersonIndividual — DJ, performer, curator, organizer.
EventEventActivity at a specific time, hosted by an Organization or Person, at a Place.
Broadcast(novel)Ephemeral signal from an Organization, pinned to a Place, max 24h lifetime.
ListItemListCuratorial selection of events, organizations, or places.

Place

Schema.org Place. Physical locations, deduplicated by Google Places ID where one is available. The canonical record for an address; events and organizations link to it by id.

FieldTypeNotes
iduuidInternal Place ID. Used as FK from Events, Organizations, etc.
namestringCanonical name.
addressPostalAddressSchema.org PostalAddress object: streetAddress, addressLocality, addressRegion, postalCode, addressCountry.
geoGeoCoordinates{ latitude, longitude }. Always present.
identifierPropertyValue[]External IDs. Common entry: { propertyID: "googlePlaceId", value: "ChIJ..." }.
 
{
  "id": "f1b2c3d4-...",
  "name": "Espresso Co",
  "address": {
    "streetAddress": "1234 Main St",
    "addressLocality": "Philadelphia",
    "addressRegion": "PA",
    "postalCode": "19125",
    "addressCountry": "US"
  },
  "geo": { "latitude": 39.97, "longitude": -75.13 },
  "identifier": [
    { "propertyID": "googlePlaceId", "value": "ChIJ..." }
  ]
}

Two place IDs in the system. Place.id is the internal Commons UUID. Place.identifier[].value with propertyID: "googlePlaceId" is the Google Places API ID. Events still expose a top-level place_id field that contains the Google ID for backward compatibility — do not confuse with Place.id.

An Organization may have a single location (the primary place) and additional places via the organization_places link table — chains, pop-ups, shared spaces. Verification attaches to the Organization, not to any place.

Event

Schema.org Event. Activity at a specific time, at a Place, hosted by an Organization or Person. Events are the most-used type in the substrate and have the longest list of properties — the table below covers the core; the full schema is in openapi.json.

FieldNotes

Broadcast

Ephemeral signal from a verified Organization, pinned to a Place. Maximum 24h lifetime. No direct Schema.org analog; SpecialAnnouncement was checked and rejected as a fit for ephemeral commercial signals — conventions for datePosted and expires borrowed from there.

{
  "id": "...",
  "message": "Half off all sandwiches until we sell out",
  "datePosted": "2026-05-05T14:00:00-04:00",
  "expires": "2026-05-05T18:00:00-04:00",
  "status": "active",
  "organization": { "id": "...", "name": "Bubs", "verified": true },
  "location": { "id": "...", "name": "Bubs", "geo": {...} },
  "source": { "publisher": "bubs", "method": "service", "contributor": "Holler", "collected_at": "..." }
}

Broadcast creation is not gated on the organization being verified — apps decide whether to surface unverified broadcasts in their feeds. verified=true + verified_by=... filters on GET /v1/broadcasts let consumer apps slice editorially.

List

Schema.org ItemList. Curatorial selections by an Organization or Person. Items are polymorphic — a single list can hold events, organizations, places, or any mix.

{
  "id": "...",
  "slug": "this-weekends-picks",
  "name": "This Weekend's Picks",
  "description": "Five things worth your Saturday",
  "curator": { "@type": "Person", "id": "...", "name": "Olive" },
  "itemListOrder": "Ascending",
  "numberOfItems": 5,
  "itemListElement": [
    {
      "@type": "ListItem",
      "position": 1,
      "item": { "@type": "Event", "id": "...", "name": "..." },
      "curatorNote": "If you only see one thing, see this."
    }
  ]
}

Lists are how curator workflows surface in the substrate. A curator (Organization or Person) builds a list; the items can be events they recommend, organizations worth watching, places worth knowing about — or all three in one list.

Filter composition

Filters are applied at the URL query level. Compose them freely; all are optional.

FilterApplies toEffect
verified=trueorganizations, persons, broadcastsOnly verified targets. Verification is computed from active rows in account_verified_identifiers.
verified_by=app1,app2organizations, persons, broadcastsVerified by any of the listed apps. Use the appName from GET /v1/verifiers.
not_verified_by=app-xorganizations, persons, broadcastsExcludes targets verified only by the listed apps.
created_by_contributor=AppNamebroadcasts, eventsFilters to records whose source.contributor matches the supplied app name.
kind=local_businessorganizationsSubtype filter. See the Organization kinds.
near=lat,lngevents, places, organizations, broadcastsCoordinates as "39.97,-75.13". Pair with radius_km.
radius_km=Nevents, places, organizations, broadcastsProximity radius. Required when using near.
q=textevents, places, organizations, persons, listsText search across name and description.
category=slugeventsSingle category filter.
tag=slugeventsOne or more tags. Multiple values: AND semantics.
start_after, start_beforeeventsISO 8601 date or datetime.
collapse_series=trueeventsDeduplicates recurring events to the next upcoming instance.
group_id=uuideventsFilter to events with the given organizer (legacy field name; expects an Organization id).

Filter composition is the editorial primitive. App C trusts a different verifier set than App B; both express that as URL parameters. There is no default firehose — apps construct their own slice.

Pagination & rate limits

List endpoints accept limit (1–200, default 50) and offset (default 0). Response shape:

{
  "meta": { "total": 142, "limit": 50, "offset": 0, "spec": "neighborhood-api-v0.2", "license": "CC-BY-4.0" },
  "events": [ ... ]
}

Rate limit: 1,000 requests/hour per IP — or per API key when an X-API-Key header is sent. Limits are returned in standard RateLimit-* headers. 429 response indicates the current window is exhausted; backoff and retry after the window rolls over.

Cache hints: read responses include Cache-Control: public, max-age=60 for events, organizations, persons, places, lists, and verifiers. Broadcasts use a shorter max-age=15 because they're ephemeral. Honor these on the consumer side to keep both your costs and Commons load down.

4Writing data

Writes flow through the service tier. There is no self-service write path — service keys are operator-issued after a brief onboarding conversation. Two effective tiers exist: Browse (read, no auth or basic API key for higher rate limit) and Service (write, with optional is_admin variant).

Getting a service key

Email hi@neighborhood-commons.org with the following:

  • App name and URL.
  • What you're building. One paragraph is fine.
  • How you plan to verify the organizations you onboard. In-person? Video call? Domain email only? This determines what verification_authority the operator grants your key.
  • Team contact email.
  • Expected first-week write volume. Used to size rate limits.

Typical turnaround is one business day. The operator will reply with the raw key string (saved once — cannot be recovered) and confirm what's set on it.

brand_config

Verification emails are sent from the Commons-shared Resend account. Two valid configurations:

TierSender shownResend cost
Display-only (recommended for v1) YourApp <verify@neighborhood-commons.org> Free
Full domain YourApp <verify@yourapp.com> $20/mo Resend Pro + DNS setup

Most email clients show the display name first and prominently — the display-only tier reads as your brand to the user without requiring a separate verified domain. Subject and body are under your control either way.

The full-domain upgrade is a single brand_config field change with no code impact on your side once your domain is verified in Resend.

Scoping rules

  • Reads are unrestricted. Service keys can read any public data.
  • Writes are scoped: a service key can only create/update/delete data for organizations linked to it via api_key_organization_links.
  • Cross-organization writes return 403 NOT_LINKED.
  • Admin keys (is_admin=true, currently only operator tooling) bypass scoping.

Places — register a venue

Idempotent on googlePlaceId. If a Place with the supplied Google Place ID already exists, the response is 200 with the existing record. Otherwise 201 with the new one.

$ curl -X POST "{{baseUrl}}/api/v1/service/places" \
  -H "X-API-Key: $NC_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Bubs",
    "googlePlaceId": "ChIJ...",
    "address": {
      "streetAddress": "1234 Main St",
      "addressLocality": "Philadelphia",
      "addressRegion": "PA",
      "postalCode": "19125"
    },
    "geo": { "latitude": 39.97, "longitude": -75.13 }
  }'

Organizations — create, link, update

Three relevant endpoints: create a new Organization (auto-links the calling key), link your key to an existing Organization, or update an Organization you're already linked to.

$ curl -X POST "{{baseUrl}}/api/v1/service/organizations" \
  -H "X-API-Key: $NC_KEY" -H "Content-Type: application/json" \
  -d '{
    "name": "Bubs",
    "kind": "local_business",
    "description": "Community board game shop",
    "url": "https://bubs.example",
    "telephone": "+12155550100",
    "email": "hi@bubs.example",
    "primaryPlaceId": "PLACE_UUID"
  }'

# Link to an existing Organization (if another app created it first)
$ curl -X POST "{{baseUrl}}/api/v1/service/organizations/link" \
  -H "X-API-Key: $NC_KEY" -H "Content-Type: application/json" \
  -d '{ "organizationId": "ORG_UUID" }'

# Update fields on an Organization linked to this key
$ curl -X PATCH "{{baseUrl}}/api/v1/service/organizations/ORG_UUID" \
  -H "X-API-Key: $NC_KEY" -H "Content-Type: application/json" \
  -d '{ "description": "Updated bio.", "telephone": "+12155550101" }'

Image uploads (logo, hero image) are JSON-base64: POST /v1/service/organizations/:id/logo and POST /v1/service/organizations/:id/image with body { "image": "<base64>" }. Magic-byte check, Sharp re-encoding, R2 upload — same pipeline as event images.

Persons

Create a Person record for performers, curators, or individual hosts. Person records are append-only for non-admin keys in 1.0 — operator-tier keys edit them. Person-link semantics (analogous to api_key_organization_links) ship in a later minor version.

$ curl -X POST "{{baseUrl}}/api/v1/service/persons" \
  -H "X-API-Key: $NC_KEY" -H "Content-Type: application/json" \
  -d '{
    "name": "DJ Karma",
    "alternateName": "DJ K",
    "description": "Philly-based DJ specializing in soul and disco.",
    "jobTitle": "DJ",
    "sameAs": ["https://soundcloud.com/djkarma"]
  }'

Events — using the new organizer model

Event creation predates 1.0 and accepts the existing ServiceEventInput shape. The body field is named account_id for backward compatibility but expects an Organization id. After 1.0 you can also reassign an event's organizer:

$ curl -X PATCH "{{baseUrl}}/api/v1/service/events/EVENT_UUID/organizer" \
  -H "X-API-Key: $NC_KEY" -H "Content-Type: application/json" \
  -d '{ "organizerOrganizationId": "ORG_UUID" }'

# Or assign to a Person (mutually exclusive with organizerOrganizationId)
$ curl -X PATCH "{{baseUrl}}/api/v1/service/events/EVENT_UUID/organizer" \
  -H "X-API-Key: $NC_KEY" -H "Content-Type: application/json" \
  -d '{ "organizerPersonId": "PERSON_UUID" }'

Broadcasts — ephemeral signals

Maximum 24h lifetime. Body: organizationId, placeId, message (≤280 chars), expires (ISO 8601, must be future, <=24h ahead).

$ curl -X POST "{{baseUrl}}/api/v1/service/broadcasts" \
  -H "X-API-Key: $NC_KEY" -H "Content-Type: application/json" \
  -d '{
    "organizationId": "ORG_UUID",
    "placeId": "PLACE_UUID",
    "message": "Half off sandwiches until we sell out",
    "expires": "2026-05-05T18:00:00-04:00"
  }'

# Retract early
$ curl -X POST "{{baseUrl}}/api/v1/service/broadcasts/BROADCAST_UUID/retract" \
  -H "X-API-Key: $NC_KEY"

Verification gate: broadcast creation does not require the organization to be verified. Verification is a read-time consumer-app filter. Apps editorialize.

Lists — curatorial workflows

Two-step: create the list, then add items. Items are polymorphic — events, organizations, places, or any mix.

# Create the list (curator can be 'organization' or 'person')
$ curl -X POST "{{baseUrl}}/api/v1/service/lists" \
  -H "X-API-Key: $NC_KEY" -H "Content-Type: application/json" \
  -d '{
    "name": "This Weekend's Picks",
    "description": "Five things worth your Saturday",
    "curator": { "type": "person", "id": "PERSON_UUID" }
  }'

# Add an item by position
$ curl -X POST "{{baseUrl}}/api/v1/service/lists/LIST_UUID/items" \
  -H "X-API-Key: $NC_KEY" -H "Content-Type: application/json" \
  -d '{
    "position": 1,
    "itemType": "event",
    "itemId": "EVENT_UUID",
    "curatorNote": "If you only see one thing, see this."
  }'

# Remove an item at position
$ curl -X DELETE "{{baseUrl}}/api/v1/service/lists/LIST_UUID/items/3" \
  -H "X-API-Key: $NC_KEY"

Person-curated lists require an admin key for edits in 1.0 (the api_key_organization_links pattern doesn't extend to Person yet). If you're working with a Person curator and need self-service editing, contact the operator — admin support can issue a key with appropriate authority.

Disputes

Used to flag a verified target as misattributed. Records the dispute for operator review; no automated action in 1.0.

$ curl -X POST "{{baseUrl}}/api/v1/service/disputes" \
  -H "X-API-Key: $NC_KEY" -H "Content-Type: application/json" \
  -d '{
    "targetType": "organization",
    "targetId": "ORG_UUID",
    "reason": "Imposter — verified email manager@bubs.example does not match the actual venue.",
    "submitterContact": "concerned@example.com"
  }'

5Verification

Verification is a process the Commons orchestrates and an attribute apps consume. The Commons routes; apps follow. Submission endpoints reject mismatches with 409 WRONG_METHOD pointing at the correct path.

The flow

Step 1 — Discover the path. Given a target and identifier, the Commons returns which submission endpoint to call:

$ curl "{{baseUrl}}/api/v1/service/verifications/path?\
target_type=organization&target_id=ORG_UUID&\
identifier_type=email&identifier_value=manager@bubs.example" \
  -H "X-API-Key: $NC_KEY"

Three possible response shapes:

// Business-domain email on a heavy-rigor organization
{
  "alreadyVerified": false,
  "requiredMethod": "domain_email_loop",
  "endpoint": "/v1/service/verifications/challenges",
  "reason": "business_email_domain"
}

// Personal-domain email (gmail, yahoo, etc.) on a heavy-rigor organization
{
  "alreadyVerified": false,
  "requiredMethod": "manual_review",
  "endpoint": "/v1/service/verifications/manual",
  "reason": "personal_email_domain"
}

// Already verified — your UI should skip this and confirm the existing record
{
  "alreadyVerified": true,
  "existingIdentifier": {
    "identifierType": "email",
    "method": "manual_review",
    "verifiedAt": "...",
    "verifiedByApp": "Merrie"
  }
}

Step 2a — Auto-track (challenge / confirm). Used when the path returned domain_email_loop. Issue a code; the Commons emails it from your brand_config sender:

$ curl -X POST "{{baseUrl}}/api/v1/service/verifications/challenges" \
  -H "X-API-Key: $NC_KEY" -H "Content-Type: application/json" \
  -d '{
    "targetType": "organization",
    "targetId": "ORG_UUID",
    "identifierType": "email",
    "identifierValue": "manager@bubs.example"
  }'

# Response: { "challengeId": "...", "expiresAt": "..." }

# User pastes the code in your UI; you submit
$ curl -X POST "{{baseUrl}}/api/v1/service/verifications/challenges/CHALLENGE_ID/confirm" \
  -H "X-API-Key: $NC_KEY" -H "Content-Type: application/json" \
  -d '{ "code": "123456" }'

# Response on match: { "status": "verified", "verifiedAt": "...", "method": "domain_email_loop", "identifier": {...} }
# Response on mismatch: { "status": "rejected", "reason": "invalid_code" }

Codes are six digits. Challenges expire after 30 minutes. Five wrong attempts on the same challenge return 429 RATE_LIMIT.

Step 2b — Manual track (structured evidence). Used when the path returned manual_review. Submit evidence; if your key has verification_authority covering the method, it auto-approves; otherwise it queues for admin review:

$ curl -X POST "{{baseUrl}}/api/v1/service/verifications/manual" \
  -H "X-API-Key: $NC_KEY" -H "Content-Type: application/json" \
  -d '{
    "targetType": "organization",
    "targetId": "ORG_UUID",
    "identifierType": "email",
    "identifierValue": "manager@gmail.com",
    "evidence": {
      "phone": "+12155550100",
      "verifiedVia": "in_person",
      "reviewerAttestation": "Met owner Jane at the bar, confirmed identity via driver license; business address matches.",
      "reviewerAccountId": "internal-reviewer-id",
      "businessAddressObserved": true,
      "idDocumentObserved": true
    }
  }'

# With verification_authority: { "status": "verified", "verifiedAt": "...", "method": "manual_review", "identifier": {...} }
# Without:                     { "status": "pending", "reviewId": "..." }

Required evidence fields: phone, verifiedVia (in_person | video_call), reviewerAttestation, reviewerAccountId, businessAddressObserved, idDocumentObserved. Missing or malformed fields return 400 VALIDATION_ERROR; submission to the wrong path (e.g., business email through manual) returns 409 WRONG_METHOD.

verification_authority

An operator-set JSON array on each service key listing methods the key may auto-approve. Granted after the operator reviews your verification process during onboarding. Format: method:context. Examples:

ValueMeaning
["manual_review:in_person"]Auto-approve manual reviews where verifiedVia is in_person. Queues for admin otherwise.
["manual_review:in_person", "manual_review:video_call"]Both methods auto-approve.
null / []No authority. All manual submissions queue for admin review.
["*"]Operator/admin wildcard. Reserved for Studio.

Apps without authority can still submit manual-review evidence — those submissions just queue. Typical turnaround for admin review is one business day.

Reputation graph

Every approval includes the approving app's stable name (snapshot of brand_config.app_name at approval time). The reputation graph is public:

$ curl "{{baseUrl}}/api/v1/verifiers"

# Returns one entry per app with: appName, firstApprovalAt, approvalCount,
# activeCount, revokedCount, methods used.

# Audit a specific verifier's recent work
$ curl "{{baseUrl}}/api/v1/verifiers/Holler/recent_approvals"

Apps reading the Commons compose verified_by filters that match their own trust policy. Sloppy verification is filtered out by other apps. Market discipline replaces central authority — and approving apps have a direct economic incentive to verify carefully, since their approvals being filtered means the businesses they onboarded lose reach across the rest of the ecosystem.

6Webhooks

Subscribe to push notifications instead of polling. Each delivery is HMAC-SHA256 signed. Failed deliveries are retried with exponential backoff; subscriptions that fail repeatedly are auto-disabled.

Setup

Subscribe with a service-tier API key:

$ curl -X POST "{{baseUrl}}/api/v1/webhooks" \
  -H "X-API-Key: $NC_KEY" -H "Content-Type: application/json" \
  -d '{
    "url": "https://yourapp.example/webhooks/commons",
    "event_types": ["event.created", "event.updated", "event.deleted"]
  }'

# Response includes a signing_secret. Save it — it cannot be recovered.
# All deliveries to this subscription are signed with this secret.

# Test the endpoint with a synthetic delivery
$ curl -X POST "{{baseUrl}}/api/v1/webhooks/SUBSCRIPTION_ID/test" \
  -H "X-API-Key: $NC_KEY"

# Inspect recent delivery attempts (debugging)

Signature verification

Each delivery carries an X-NC-Signature header containing the HMAC-SHA256 of the raw request body, keyed by your subscription's signing_secret. Verify before trusting any delivery.

// Node.js example — verify before processing
import { createHmac, timingSafeEqual } from 'crypto';

function verifyWebhook(rawBody: Buffer, signatureHeader: string, secret: string): boolean {
  // Header format: "sha256=<hex>"
  const [algo, sig] = signatureHeader.split('=');
  if (algo !== 'sha256' || !sig) return false;

  const expected = createHmac('sha256', secret).update(rawBody).digest('hex');

  // Constant-time compare; both buffers must be the same length
  const sigBuf = Buffer.from(sig, 'hex');
  const expectedBuf = Buffer.from(expected, 'hex');
  if (sigBuf.length !== expectedBuf.length) return false;
  return timingSafeEqual(sigBuf, expectedBuf);
}

// Express handler
app.post('/webhooks/commons', express.raw({ type: 'application/json' }), (req, res) => {
  const sig = req.headers['x-nc-signature'] as string;
  if (!verifyWebhook(req.body, sig, process.env.COMMONS_WEBHOOK_SECRET!)) {
    return res.status(401).end();
  }
  const payload = JSON.parse(req.body.toString());
  // ... process the delivery
  res.status(204).end();
});

Verify against the raw request body, not a re-stringified version — different JSON serializers produce different byte sequences and the signature won't match.

Retry behavior

Deliveries that fail (network error, non-2xx response, timeout) retry with exponential backoff: ~30s, 2m, 10m, 1h, 6h. After five consecutive failures, the subscription is marked disabled and stops receiving deliveries until the operator re-enables it. Inspect GET /v1/webhooks/:id/deliveries for failure reasons.

Idempotency: Commons may retry a delivery that actually succeeded (e.g., your server returned 2xx but Commons didn't see the response). Use delivery_id as your idempotency key — store it server-side and skip processing on duplicates.

Stability

The 1.0.0 spec is stable. Future minor versions add types, fields, and endpoints additively without breaking existing consumers. Removals or renames require a 2.0.0 release with strong justification — measured in years, not months. Watch the Changelog for every contract-affecting change.

If something in this Guide contradicts openapi.json on a matter of fact, trust the spec and file an issue. The Spec wins. The Guide explains. The Log dates.
